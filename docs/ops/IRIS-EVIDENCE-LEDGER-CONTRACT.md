# Iris Evidence Ledger Contract (proposed)

**Status:** design contract only. This document does not claim that a ledger service, repository inspector, or execution engine has been implemented.

## Purpose

Give Iris a durable, reviewable record of what it proposed, what tools actually did, and what evidence supports each status. A model-generated summary is not evidence by itself.

## Required record fields

Every task record should contain:

- `schema_version`: versioned contract identifier.
- `task_id`: unique stable identifier.
- `created_at` and `updated_at`: UTC timestamps from the recording service.
- `goal`: bounded human-readable objective.
- `pillar_ids`: one or more of the four strategic pillars.
- `status`: one of `IDEA`, `SCAFFOLDED`, `LOCAL-VERIFIED`, `STAGING-VERIFIED`, `PRODUCTION-DEPLOYED`, `LIVE-VERIFIED`, or `BLOCKED/DRIFTED`.
- `proposed_steps`: plan text, explicitly labelled as proposed.
- `evidence[]`: evidence entries with source, observed time, outcome, and immutable content digest.
- `authorization`: decision reference, authority, scope, action, request ID, input digest, and expiry where applicable. Store references and decision metadata, never secrets or authentication material.
- `changes[]`: repository, branch, commit SHA, and changed paths, if a change actually occurred.
- `verification[]`: test/check name, exact revision tested, command or workflow identifier, outcome, and link to inspectable output.
- `limitations[]`: unresolved assumptions, missing access, skipped checks, and known failures.
- `previous_record_digest`: digest of the preceding ledger record, where append-only chaining is supported.

## Evidence rules

1. A proposal generated by a model is `IDEA` or `SCAFFOLDED`, never tested or deployed by implication.
2. `LOCAL-VERIFIED` requires a reproducible local check and the exact revision or artifact digest.
3. `STAGING-VERIFIED` requires evidence from the actual staging environment and exact deployed revision.
4. `PRODUCTION-DEPLOYED` requires a deployment event tied to a specific revision and environment.
5. `LIVE-VERIFIED` additionally requires post-deployment checks against the live system.
6. Failed, skipped, stale, missing, or revision-mismatched checks cannot satisfy a gate. Mark the task `BLOCKED/DRIFTED` when evidence is insufficient or live state differs from the declared revision.
7. Never convert model-generated text into a test result, authorization decision, financial recovery, or deployment fact.
8. Hashes establish content identity, not truthfulness of the source. Keep the source URI/identifier and retrieval timestamp with each digest.

## Authorization and side effects

- Trinity is the sole authorization authority.
- A valid authorization must bind the principal, action, request ID, input digest, and scope; reject missing, stale, replayed, or mismatched decisions.
- For any side effect, perform the authorization check before an atomic idempotency claim; do not execute if either gate fails.
- Read-only inspection must use least-privilege credentials and explicit repository allowlists.
- The planning-only Iris bridge cannot write ledger entries that claim an action happened unless a trusted recorder receives independent tool results.

## Secret handling

Never record bearer tokens, API keys, private keys, passkey/biometric material, full authorization headers, or unredacted environment dumps. Redact sensitive request/response fields before persistence. A digest of a secret is not a substitute for a secret-management policy.

## Minimal acceptance tests before implementation

- Reject unknown or invalid status values.
- Reject records missing task ID, exact revision, or source for claimed verification.
- Reject promotion to a stronger status without required evidence.
- Detect evidence bound to a different commit/deployment revision.
- Detect duplicate request IDs for side-effecting actions.
- Prove missing or invalid Trinity authorization fails closed.
- Prove logs and serialized records contain no configured secret sentinel values.
- Verify append-only behavior and digest-chain validation if chaining is enabled.

## Rollout sequence

1. Implement the schema and pure validation tests.
2. Add a trusted append-only recorder, initially writing only synthetic test evidence.
3. Add read-only GitHub inspection with an allowlist and record the exact commit SHA inspected.
4. Link CI workflow results and logs as evidence; do not infer success from a branch name.
5. Run isolated staging tests with no repository writes or deployment privileges.
6. Review threat model and authorization contracts before any separately approved execution capability.

This contract is a proposed acceptance standard, not proof that any of these components already exist.
