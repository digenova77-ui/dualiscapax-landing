# Iris Read-Only Repository Inspector — Implementation Contract

**Status:** implementation specification; not a live inspector. No repository writes, shell execution, deployments, or production changes are enabled by this document.

## Goal

Allow Iris to inspect explicitly approved repository files and report reproducible evidence about the exact source revision. The first implementation must be read-only and separately testable from the planning model.

## API shape

A proposed internal request:

```json
{
  "repository": "digenova77-ui/dualiscapax-landing",
  "path": "workers/iris-agent/src/index.ts",
  "ref": "main"
}
```

The server must validate the request before making any upstream call. Do not accept arbitrary URLs, owner names, repository names, or paths from the caller.

## Repository allowlist for the first slice

- digenova77-ui/dualiscapax-landing
- digenova77-ui/dualiscapax-deploy
- digenova77-ui/dccp-world
- digenova77-ui/dualiscapax-hud
- digenova77-ui/dualiscapax-law-core
- digenova77-ui/coin-repo
- digenova77-ui/abc-agency
- digenova77-ui/efuse-unity

Expand only through reviewed changes. An allowlist is not a guarantee that every repository is accessible to the configured credential.

## Request validation

- Accept only JSON POST requests with a strict byte limit.
- Require the dedicated Iris bridge gate and exact allowed-origin policy.
- Reject unknown repositories, empty paths, absolute paths, backslashes, path traversal segments, excessive path/ref lengths, and sensitive path names such as environment files, private keys, credentials, and secret configuration.
- Reject arbitrary URLs and redirects supplied by the caller.
- Use a fixed GitHub API host and construct the path only after validation.
- Limit response size; reject directories, symlinks, unsupported encodings, binary files, and oversized blobs.
- Return safe, bounded errors without upstream response bodies or credential details.

## Evidence response

For a successful observation, return:

- status: `read-only-observation`
- repository, requested ref, resolved source path
- upstream blob SHA and resolved commit SHA when available
- SHA-256 of the exact decoded file bytes
- byte count and trusted source URL
- file content only when it is within the configured size limit
- observation timestamp generated by the service
- explicit limitations: this observation does not prove runtime behavior, test success, authorization, or deployment

The upstream commit must be resolved and recorded; a moving branch name alone is not sufficient evidence. If the provider response does not establish the resolved commit SHA, return the observation as incomplete rather than claiming revision-pinned evidence.

## Credential model

Use a narrowly scoped read-only GitHub credential stored only in the Worker secret store. Never place credentials in source, client code, logs, returned JSON, error messages, or evidence records. Do not request broader permissions than required. Rotate the credential if exposure is suspected.

## Acceptance tests

1. Allow an approved repository and a safe source path.
2. Reject a repository not on the allowlist.
3. Reject absolute paths, backslashes, traversal, empty path segments, and sensitive filenames.
4. Reject malformed JSON, wrong methods, wrong content type, excessive request bytes, and invalid gate credentials.
5. Reject redirects to non-GitHub hosts and never follow caller-supplied URLs.
6. Reject directory responses, binary/unsupported content, and oversized files.
7. Verify the returned digest against the exact decoded bytes.
8. Verify the resolved commit is captured and is stable for the observation.
9. Prove the configured read credential is never included in output or logs.
10. Prove the endpoint has no write API calls and no shell/process capability.
11. Prove missing configuration fails closed.
12. Ensure all errors carry `not_verified` where the source observation could not be completed.

## Rollout gates

- Gate A: pure request validation tests pass.
- Gate B: mocked upstream tests prove allowlist, URL construction, response limits, redaction, and digest correctness.
- Gate C: CI passes on the exact commit SHA.
- Gate D: staging secret and account configuration are confirmed; staging deployment requires explicit approval.
- Gate E: staging tests inspect a harmless known file and compare the returned digest with an independently calculated digest.
- Gate F: only after separate review may the inspector feed a ledger; it must not authorize writes.

**No gate is passed by this specification alone.**
